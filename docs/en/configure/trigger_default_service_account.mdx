# Triggers Default ServiceAccount

The 4.0 line does not install the enhancement RBAC controller. On Kubernetes,
omitting `spec.serviceAccountName`, or setting it to an empty string, selects the
`default-service-account` value in `config-defaults-triggers`. Without an override,
Triggers uses `default`. This account is not automatically granted Triggers
permissions. On OpenShift, the existing operator default remains `pipeline`.

Create and authorize the intended account in each relevant namespace before
selecting it explicitly on an EventListener. To set a global default for new
listeners, use the existing TektonConfig field:

```yaml
apiVersion: operator.tekton.dev/v1alpha1
kind: TektonConfig
metadata:
  name: config
spec:
  trigger:
    default-service-account: custom-trigger-sa
```

This configuration selects an account; it does not create accounts or grant
permissions. It does not affect PipelineRun or TaskRun account selection.

## Restore the Existing Default

Removing `spec.trigger.default-service-account`, or setting it to an empty
string, restores the packaged configuration. Additional options for the same
ConfigMap retain their existing priority and must also be removed when restoring
the default. On Kubernetes, the effective key is absent when the packaged
ConfigMap has no override, and Triggers falls back to `default`.

Each reconciliation now starts from an unchanged source manifest. Removed
account values and options do not carry over from an earlier reconciliation in
the same operator process. Express intentional customizations in TektonConfig
or its options instead of editing the managed ConfigMap directly.

Existing EventListeners retain their stored nonempty account names. This fix
neither switches them to `triggers-default-sa` nor automatically provisions that
account. An administrator must explicitly repair a confirmed account-related
listener failure after reviewing the required permissions.

## Configuration Withdrawal

Overrides in `spec.trigger.options.configMaps` are removed from the installed
ConfigMap when withdrawn, including overrides present at first installation.
For a packaged ConfigMap such as `config-defaults-triggers`, removing the options
data, leaving an empty ConfigMap options entry, or removing that entry restores
the current declared settings. Explicit empty option values remain overrides
until removed. For an additional ConfigMap created only by options, keep its
entry and withdraw individual data keys to remove those managed values. Removing
that additional object's entire entry retains the existing InstallerSet resource
lifecycle behavior; it does not guarantee deletion of the previously installed
ConfigMap or its data.

For older installations, the operator uses the previous InstallerSet declarations
to identify managed data keys. Other keys added directly by an administrator are
preserved. If an older version has already lost both the prior declaration and
its application history, an unexplained ConfigMap-only value cannot be identified
as a withdrawn override automatically. Review such values against the intended
configuration and remove only confirmed obsolete entries.
