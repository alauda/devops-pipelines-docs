# Quick Start

## Installation of Tekton Results

This document explains how to install Tekton Results using an **existing database**.

:::note
Currently, the built-in PostgreSQL database is not supported, please use an external database.

About external database please refer to [Using PostgreSQL from Data Services](./configure/database_configuration.mdx#using-postgresql-from-data-services)
:::

:::tip
Tekton Results supports storing logs in various storage backends. **S3-compatible object storage (such as AWS S3, Ceph, MinIO) is now the recommended approach** for scalable and durable log retention. For detailed S3 storage configuration, see the [S3 Storage Configuration Guide](./configure/s3_storage_configuration.mdx). Local PVC storage is not recommended for production use.
:::

### Prerequisites

1. Tekton Pipelines must be installed in the cluster.

   :::tip
   The following instructions assume that you have installed Results into the `tekton-pipelines` namespace by default.

   If you have installed it into a different namespace, please replace `tekton-pipelines` with your namespace.
   :::

2. Store the database account.

   Tekton Results connects to PostgreSQL with the user name and password stored in a
   [Kubernetes Secret](https://kubernetes.io/docs/concepts/configuration/secret/). Create the `Secret` before installation, with the database user that Tekton Results connects as, for example a dedicated `result` user. By default, Tekton Results expects this `Secret` to have the following attributes:

   - Namespace: `tekton-pipelines`
   - Name: `tekton-results-postgres`
   - Including the following fields:
     - `POSTGRES_USER=<your_username>`
     - `POSTGRES_PASSWORD=<your_password>`

   You can quickly generate a `Secret` using the following commands. Run the `read -rs` line on its own, type the database password and press Enter: `read -rs` does not show it, so it does not appear on the screen or in the shell history. In a shell without bracketed paste, such as bash before 5.1, `read` takes the next line of a pasted block as the password. Run the commands in bash or zsh: in a POSIX `sh` such as `dash`, `read -rs` fails and leaves the variable empty:

   ```bash
   read -rs DB_PASSWORD
   ```

   Then create the `Secret`. `unset` removes the password from the shell after the `Secret` is created:

   ```bash
   kubectl create secret generic tekton-results-postgres --namespace="tekton-pipelines" --from-literal=POSTGRES_USER=<your_username> --from-literal=POSTGRES_PASSWORD="$DB_PASSWORD"
   unset DB_PASSWORD
   ```

3. Generate a certificate/key pair. Note: Any certificate management software can be used for this purpose!

   Tekton Results expects the certificate/key pair to be stored in a
   [TLS Kubernetes Secret](https://kubernetes.io/docs/concepts/configuration/secret/#tls-secrets) named `tekton-results-tls`.

   - Generate a new self-signed certificate

      ```sh
      openssl req -x509 \
        -newkey rsa:4096 \
        -keyout key.pem \
        -out cert.pem \
        -days 365 \
        -nodes \
        -subj "/CN=tekton-results-api-service.tekton-pipelines.svc.cluster.local" \
        -addext "subjectAltName = DNS:tekton-results-api-service.tekton-pipelines.svc.cluster.local"
      ```

      :::tip
      If your `openssl` version is too low and does not support some parameters, please upgrade your `openssl` version from [openssl binaries](https://github.com/openssl/openssl/wiki/Binaries) .
      :::

   - Create a new TLS Secret from the certificate.

      ```sh
      kubectl create secret tls -n tekton-pipelines tekton-results-tls \
        --cert=cert.pem \
        --key=key.pem
      ```

4. (For quick start only) Create a `PVC` if you are using the legacy `File` storage type (not recommended for production).

   :::warning
   PVC-based local storage is not recommended for production use. **S3-compatible object storage is the recommended approach** for scalable and durable log retention. For S3 storage configuration, see the [S3 Storage Configuration Guide](./configure/s3_storage_configuration.mdx).
   :::

   If you still need to use PVC for testing purposes:

   ```sh
   cat <<EOF | kubectl create -f -
   apiVersion: v1
   kind: PersistentVolumeClaim
   metadata:
     name: tekton-logs
     namespace: tekton-pipelines
   spec:
     accessModes:
       - ReadWriteOnce  # The access mode indicating it can be read and written by a single node
     resources:
       requests:
         storage: 100Gi  # The requested storage size
   EOF
   ```

   - Please adjust the PVC size as needed.
   - The sample sets no `storageClassName`, so the PVC uses the default StorageClass of the cluster, which `kubectl get storageclass` marks with `(default)`. If the cluster has none, add `storageClassName: <storage-class>` to `spec`; without a StorageClass the PVC can stay `Pending`.
   - Note: This is only required if using the legacy File storage type.

### Installing using operator CRD \{#installing-using-operator-crd}

The operator already created the `TektonConfig` named `config`. Merge the following `spec.result` fields into it; `disabled: false` installs Tekton Results. The merge keeps the other `TektonConfig` fields, including `spec.targetNamespace`, the namespace where Tekton Results is deployed.

```sh
cat <<EOF > tekton-results-patch.yaml
spec:
  result:
    # Install Tekton Results
    disabled: false
    # Update with database address
    db_host: <database_host>
    db_port: 5432
    db_name: <database_name>
    # Use external database
    is_external_db: true
    # secret containing database account information created earlier
    db_secret_name: tekton-results-postgres
    # Basic settings
    server_port: 8080
    # Disable authentication (for testing only, see auth_disable below)
    auth_disable: true
    db_enable_auto_migration: true
    log_level: debug
    # Use logs storage service
    logs_api: true
    logs_type: File
    logging_pvc_name: tekton-logs
    # logs_type: S3  # Recommended: S3-compatible storage for scalable log retention
    # secret_name: tekton-results-s3-credentials  # Secret containing S3 credentials
    logs_path: /logs
    logs_buffer_size: 92160
    # S3 storage does not require PVC, unlike legacy File storage
EOF
kubectl patch tektonconfig config --type merge --patch-file tekton-results-patch.yaml
```

:::details
  The Tekton Results configuration fields below are nested under `spec.result` in the TektonConfig resource, except `targetNamespace`, which is `spec.targetNamespace`.
  - `disabled`: Whether Tekton Results is disabled.
    - `false`: Install Tekton Results.
  - `db_host`: The host of the database.
  - `db_port`: The port of the database.
  - `db_name`: The name of the database.
  - `is_external_db`: Must be `true`, because the built-in PostgreSQL database is not supported.
    - `true`: Use an external database.
  - `db_secret_name`: The name of the secret containing the database account information.
    - This is the secret created in the previous step.
  - `server_port`: The port of the server.
  - `targetNamespace` (`spec.targetNamespace`, not changed by the patch): The namespace where the Results is deployed.
  - `auth_disable`: Whether to disable authentication.
    - `true`: For testing only. The Results API skips its Kubernetes RBAC check and allows every request, so anyone who can reach the API can read, change and delete the results, records and logs of every namespace. This includes access through the Ingress `tektoncd-results-api` that the Tekton Results installation creates, which serves the API under the path `/results`. Turn authentication back on after the test as described in [Turn authentication back on](#turn-authentication-back-on).
  - `db_enable_auto_migration`: Whether to enable automatic database migration.
  - `log_level`: The level of the log.
  - `logs_api`: Whether to enable the logs API.
    - `true`: Enable the logs API.
  - `logs_type`: The type of the logs.
    - `File`: Store logs in a file (not recommended for production use).
    - `S3`: Store logs in S3-compatible object storage (e.g., AWS S3, Ceph, MinIO). **This is the recommended approach** for scalable and durable log retention. For detailed configuration, see the [S3 Storage Configuration Guide](./configure/s3_storage_configuration.mdx).
  - `secret_name`: The name of the secret containing the S3 account information. For detailed configuration, see the [S3 Storage Configuration Guide](./configure/s3_storage_configuration.mdx).
  - `logs_path`: The path of the logs.
  - `logs_buffer_size`: The buffer size of the logs.
  - `logging_pvc_name`: The name of the PVC to store the logs (only required when using legacy File storage type).
    - This is the PVC created in the previous step (not needed for S3 storage).
:::

:::tip
About more database configuration, please refer to [PostgreSQL Configuration](./configure/database_configuration.mdx)
:::

After deployment, you can see that the status of `results-api` / `results-retention-policy-agent` / `results-watcher` is `Running`. The namespace also holds the Pods of other Tekton components; the output below is shortened to the Tekton Results Pods:

```sh
$ kubectl get pods -n tekton-pipelines

tekton-results-retention-policy-agent-c6ff5575b-prczg   1/1     Running   0          14s
tekton-results-watcher-6d7c68f576-p2gbl                 1/1     Running   0          14s
```

### Verify Functionality \{#verify-functionality}

Functionality can be verified through a simple taskrun.

#### 1. Create a `TaskRun` resource

```sh
cat <<'EOF' | kubectl create -n default -f -
apiVersion: tekton.dev/v1
kind: TaskRun
metadata:
  name: hello
spec:
  taskSpec:
    steps:
      - name: hello
        image: alpine
        command:
          - "echo"
          - "hello"
EOF
```

:::note
Replace the public `alpine` image with an image your cluster can pull, for example from an internal registry in an air-gapped environment.

The Tekton webhook rejects a `TaskRun` with an inline `taskSpec` when the cluster setting `disable-inline-spec` contains `taskrun` (see [Constrain Tekton Pipeline Execution with Kyverno](../pipelines/how_to/constrain_pipeline_execution_with_kyverno.mdx)); on such a cluster, create a `Task` with the same step and reference it with `taskRef` instead.
:::

#### 2. Wait for the task execution to complete

```sh
$ kubectl get taskruns.tekton.dev -n default -w

NAME                                         SUCCEEDED   REASON      STARTTIME   COMPLETIONTIME
hello                                        Unknown     Pending     3s
hello                                        True        Succeeded   11s         0s
```

#### 3. Use tkn-results CLI to query results

##### Preparing the CLI \{#preparing-the-cli}

> [tkn](https://github.com/tektoncd/cli/releases) is a command-line tool for interacting with Tekton. You can download it from the [official page](https://github.com/tektoncd/cli/releases).
>
> You need to build [tkn-results](https://github.com/tektoncd/results/blob/main/cmd/tkn-results/main.go) using golang. Use at least the Go version on the `go` line of `go.mod` in the branch that you check out: Results v0.19.0 has `go 1.25.8`, so it needs Go 1.25.8 or later.
>
> Do not always build from `main`. Use the release branch that matches the Tekton Results version deployed in your environment.
> You can find the Results component version in [Release Notes](../overview/release_notes.mdx#compatibility-and-support-matrix) (the `Results` column), and then checkout the corresponding branch `release-v<version>.x`.

```sh
# 1. Clone the repository
git clone https://github.com/tektoncd/results.git

# 2. Change to the project directory
cd results

# 3. Checkout the matching release branch (example: Results 0.15.x -> release-v0.15.x)
git checkout release-v<version>.x

# 4. Build the binary
go build -o tkn-results ./cmd/tkn-results/main.go

# 5. Copy the binary to a directory in your PATH
```

##### Connection behavior

> When `--addr` is not set, `tkn-results` attempts to auto port-forward to the Results API service.
>
> In many versions (including `release-v0.15.x`), the auto target is `tekton-pipelines/tekton-results-api-service`.
> If your Results deployment uses a different namespace or service name, auto mode may fail.
>
> When `--addr` is set, `tkn-results` connects to that address directly.
> In that case, you typically need to run `kubectl port-forward` yourself.

##### Fallback when auto port-forward fails

Start the port-forward in a separate terminal and keep it running while you run the `tkn results` commands; it runs in the foreground until you stop it with Ctrl+C:

```sh
kubectl port-forward -n <results-namespace> service/tekton-results-api-service 8080
```

Then, in your first terminal:

```sh
tkn results --insecure --addr localhost:8080 records list default/results/-
tkn results --insecure --addr localhost:8080 records get -o textproto default/results/<result-uid>/records/<record-uid>
tkn results --insecure --addr localhost:8080 logs list default/results/-
# With logs_type File or S3, as set on this page, the Results API serves only the
# v1alpha2 Logs API, so logs get needs --v1alpha2; without it, the command fails with
# "unknown service tekton.results.v1alpha3.Logs". The flag works even where the CLI
# marks it as deprecated:
tkn results --insecure --addr localhost:8080 --v1alpha2 logs get -o textproto default/results/<result-uid>/logs/<log-uid>
```

> With `logs_type` `File` or `S3`, the types that this page sets, the Results API serves only the v1alpha2 Logs API.
> `logs get` therefore needs the `--v1alpha2` flag; without it, the command fails with `unknown service tekton.results.v1alpha3.Logs`.
> `logs get` uses the flag to call the v1alpha2 Logs API, even where the CLI marks the flag as deprecated.


#### 4. Turn authentication back on \{#turn-authentication-back-on}

The installation patch sets `auth_disable: true`, which is for testing only. After the test, save the following merge patch as `results-auth-patch.yaml`:

```yaml
spec:
  result:
    auth_disable: false
```

Merge it, then repeat the second command until it prints `AUTH_DISABLE=false`. If it keeps printing `AUTH_DISABLE=true`, read the `TektonConfig` conditions with the third command. The Operator applies the Pipelines, event-based Pruner, Triggers and Chains components before Tekton Results and stops at a component that it cannot apply; the `ComponentsReady` condition is then `False` with a message that starts with `Components not in ready state:` and names that component:

```bash
kubectl patch tektonconfig config --type merge --patch-file results-auth-patch.yaml
kubectl get configmap tekton-results-api-config -n tekton-pipelines -o jsonpath='{.data.config}' | grep AUTH_DISABLE
kubectl get tektonconfig config -o jsonpath='{range .status.conditions[*]}{.type} {.status} {.message}{"\n"}{end}'
```

The Results API reads this setting only when it starts. Delete its Pod so that the Deployment starts a new one with the setting, then check that the new Pod is `Running`:

```bash
kubectl delete pods -n tekton-pipelines -l app.kubernetes.io/name=tekton-results-api
kubectl get pods -n tekton-pipelines -l app.kubernetes.io/name=tekton-results-api
```
