# Quick Start

This guide helps cluster administrators try queue-based pipeline admission in a test cluster in approximately 10 minutes.

## Introduction \{#introduction}

Consider a team whose build environment can handle only one PipelineRun at a time. Submitting more pipelines should queue the extra work instead of starting additional execution Pods.

This walkthrough creates an isolated queue with one concurrency slot and submits two PipelineRuns. One run executes while the other waits without creating a TaskRun or execution Pod. When the active run completes, the waiting run starts automatically. The inline pipeline sleeps briefly to make these states easy to observe; it does not require an application repository or an existing Pipeline.

## Prerequisites \{#prerequisites}

- Tekton Pipelines is ready, and you can update TektonConfig and create Kueue resources.
- Use a test cluster where Scheduler is disabled and no existing Scheduler policies need to be preserved. The enablement step changes cluster-wide component configuration.
- The platform-supported Kueue plugin and cert-manager are installed. Kueue serves `v1beta2` and includes `PipelineRun.v1.tekton.dev` in its external frameworks. See [Prepare Dependencies](./guides/manage_scheduler.mdx#prepare_dependencies).
- A BusyBox-compatible image is available in a registry reachable from the cluster. Mirror it before using an air-gapped environment.
- The `scheduler-demo` namespace, ClusterQueue, and ResourceFlavor do not already exist.

## Process overview \{#process_overview}

| Step | Operation | Result |
| --- | --- | --- |
| 1 | Enable Scheduler | The component is ready to admit pipelines. |
| 2 | Create queues and enroll the namespace | A dedicated quota limits the namespace to one admitted run. |
| 3 | Submit two PipelineRuns | One run executes and the other waits. |
| 4 | Observe admission and completion | The waiting run starts after quota is released. |
| 5 | Clean up | The example resources are removed. |

## Enable Scheduler \{#enable_scheduler}

Enable single-cluster scheduling and set the default LocalQueue name explicitly:

```bash
kubectl patch tektonconfig config --type=merge -p '{
  "spec": {
    "scheduler": {
      "disabled": false,
      "multi-cluster-disabled": true,
      "multi-cluster-role": "",
      "config.yaml": {"queueName": "pipelines-queue"}
    }
  }
}'
kubectl wait tektonscheduler/scheduler --for=create --timeout=5m
kubectl wait tektonscheduler/scheduler --for=condition=Ready --timeout=5m
```

The fields under `spec.scheduler` configure this example as follows:

| Field and value | Purpose in this example |
| --- | --- |
| `disabled: false` | Installs and enables Scheduler. |
| `multi-cluster-disabled: true` | Uses single-cluster scheduling. |
| `multi-cluster-role: ""` | Clears any Hub or Spoke role, which is unused in single-cluster mode. |
| `config.yaml.queueName: pipelines-queue` | Assigns the `pipelines-queue` LocalQueue to new runs without an explicit queue label. The queue is created in the next step. |

See [Component Settings](./configure/scheduler_configuration.mdx#component_settings) and [Webhook Settings](./configure/scheduler_configuration.mdx#webhook_settings) for complete field definitions and default values.

The first wait allows the operator to create the child resource; the second waits for installation to finish. Enabling the component does not enroll namespaces or create queues. If readiness fails, see [Troubleshoot Scheduler](./trouble_shooting/scheduler_not_ready.mdx#component_not_ready).

## Create a queue \{#create_queue}

Save the following as `scheduler_queues.yaml`:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: scheduler-demo
---
apiVersion: kueue.x-k8s.io/v1beta2
kind: ResourceFlavor
metadata:
  name: scheduler-demo
---
apiVersion: kueue.x-k8s.io/v1beta2
kind: ClusterQueue
metadata:
  name: scheduler-demo
spec:
  namespaceSelector:
    matchLabels:
      kubernetes.io/metadata.name: scheduler-demo
  resourceGroups:
    - coveredResources: [tekton.dev/pipelineruns]
      flavors:
        - name: scheduler-demo
          resources:
            - name: tekton.dev/pipelineruns
              nominalQuota: 1
---
apiVersion: kueue.x-k8s.io/v1beta2
kind: LocalQueue
metadata:
  name: pipelines-queue
  namespace: scheduler-demo
spec:
  clusterQueue: scheduler-demo
```

These resources connect the demonstration namespace to a quota pool with one PipelineRun slot. The table lists fields within each named resource:

| Resource | Field | Purpose in this example |
| --- | --- | --- |
| Namespace | `metadata.name` | Creates the dedicated `scheduler-demo` namespace for the two runs. |
| ResourceFlavor | `metadata.name` | Names the `scheduler-demo` flavor referenced by the ClusterQueue. An empty flavor is sufficient for concurrency accounting; this example sets no node placement constraints. |
| ClusterQueue | `metadata.name` | Names the cluster-scoped `scheduler-demo` quota pool referenced by the LocalQueue. |
| ClusterQueue | `spec.namespaceSelector.matchLabels` | Matches the namespace's built-in `kubernetes.io/metadata.name: scheduler-demo` label, restricting this pool to the demonstration namespace. |
| ClusterQueue | `spec.resourceGroups[].coveredResources` | Accounts for `tekton.dev/pipelineruns`, which counts admitted PipelineRuns rather than Tasks or Pods. |
| ClusterQueue | `spec.resourceGroups[].flavors[].name` | Selects the ResourceFlavor named `scheduler-demo`. |
| ClusterQueue | `spec.resourceGroups[].flavors[].resources[].name` | Selects `tekton.dev/pipelineruns` as the resource receiving quota in this flavor. |
| ClusterQueue | `spec.resourceGroups[].flavors[].resources[].nominalQuota` | Sets the quota to `1`, admitting one run at a time. |
| LocalQueue | `metadata.name` and `metadata.namespace` | Creates `pipelines-queue` in `scheduler-demo`, matching the default queue name configured above. |
| LocalQueue | `spec.clusterQueue` | Binds this namespace-local queue to the `scheduler-demo` quota pool. |

See the [ResourceFlavor API](../apis/kubernetes_apis/scheduler/resourceflavors.mdx), [ClusterQueue API](../apis/kubernetes_apis/scheduler/clusterqueues.mdx), and [LocalQueue API](../apis/kubernetes_apis/scheduler/localqueues.mdx) for complete field definitions.

Apply the resources and enroll the namespace:

```bash
kubectl apply -f scheduler_queues.yaml
kubectl wait clusterqueue/scheduler-demo --for=condition=Active --timeout=120s
kubectl label namespace scheduler-demo tekton.dev/scheduler-enabled=true
```

The `tekton.dev/scheduler-enabled=true` namespace label enables Scheduler admission for newly created PipelineRuns. See [Namespace Enrollment](./concepts/core_concepts.mdx#namespace_enrollment) for how enrollment and queue selection work together.

## Submit two runs \{#submit_runs}

Set `TEST_IMAGE` to your mirrored image, then create two runs with the following inline PipelineSpec:

```bash
# TEST_IMAGE identifies the BusyBox-compatible image available to this cluster.
export TEST_IMAGE='<your-registry>/<busybox-image>:<tag>'
# RUN gives each submission a unique name within the demonstration namespace.
for RUN in first second; do
  cat <<EOF | kubectl create -n scheduler-demo -f -
apiVersion: tekton.dev/v1
kind: PipelineRun
metadata:
  name: ${RUN}
spec:
  pipelineSpec:
    tasks:
      - name: pause
        taskSpec:
          steps:
            - name: pause
              image: ${TEST_IMAGE}
              script: |
                #!/bin/sh
                sleep 60
                echo "Pipeline completed"
  timeouts:
    pipeline: 10m
EOF
done
```

The API assigns the default `pipelines-queue` label. The run admitted first executes while the other waits; do not depend on the run names to determine admission order.

## Observe admission \{#observe_admission}

Inspect the run and queue states:

```bash
kubectl get pipelineruns -n scheduler-demo
kubectl get workloads -n scheduler-demo
kubectl get pipelineruns -n scheduler-demo \
  -o custom-columns='NAME:.metadata.name,QUEUE:.metadata.labels.kueue\.x-k8s\.io/queue-name,STATUS:.spec.status'
kubectl get pods -n scheduler-demo -l tekton.dev/pipelineRun
kubectl get taskruns -n scheduler-demo
kubectl get clusterqueue scheduler-demo -o yaml
```

Expected results:

- Both PipelineRuns have `kueue.x-k8s.io/queue-name: pipelines-queue`.
- One Workload is admitted; the other waits for quota.
- The waiting PipelineRun has `spec.status: PipelineRunPending` and has no TaskRun or execution Pod.
- After the first run completes, the waiting run executes automatically and succeeds.

Wait for both runs to complete:

```bash
kubectl wait pipelinerun/first pipelinerun/second -n scheduler-demo \
  --for=condition=Succeeded --timeout=5m
kubectl wait workloads --all -n scheduler-demo \
  --for=condition=Finished --timeout=2m
```

## Clean up \{#clean_up}

After both runs have completed, delete only the resources created by this walkthrough:

```bash
kubectl delete namespace scheduler-demo --wait=true
kubectl delete clusterqueue scheduler-demo
kubectl delete resourceflavor scheduler-demo
```

If you enabled Scheduler only for this walkthrough, follow [Disable Scheduler](./guides/manage_scheduler.mdx#disable_scheduler). Otherwise, keep it enabled for other enrolled namespaces.
