# Troubleshoot Scheduler

Start with component readiness, then follow the affected PipelineRun to its queue and Workload. The commands require permission to read the named cluster and namespace resources.

## Component is not ready \{#component_not_ready}

Inspect the parent and child conditions and check that both prerequisite APIs are present:

```bash
kubectl get tektonconfig config -o yaml
kubectl get tektonscheduler scheduler -o yaml
kubectl api-resources --api-group=kueue.x-k8s.io
kubectl api-resources --api-group=cert-manager.io
```

A missing dependency message means the operator cannot discover a required API. Install the platform-supported Kueue plugin and cert-manager, verify that Kueue serves `v1beta2`, and wait for their controllers to be ready. Use the existing Kueue installation rather than installing a second controller.

If the child is absent, verify `spec.scheduler.disabled: false`. Explicit enablement also requires `multi-cluster-disabled: true` and a nonempty `config.yaml.queueName`. See [Scheduler Configuration](../configure/scheduler_configuration.mdx#component_settings) for defaulting behavior.

## Run remains pending \{#run_remains_pending}

A pending run is expected when quota is exhausted. Inspect its label, owned Workload, and queue conditions to distinguish that case from incomplete configuration:

```bash
kubectl get pipelinerun <run> -n <namespace> -o yaml
kubectl get workloads -n <namespace> -o yaml
kubectl get localqueues -n <namespace> -o yaml
kubectl get namespace <namespace> --show-labels
kubectl get clusterqueue <clusterqueue> -o yaml
```

Use the Workload's owner reference to find the one belonging to the affected PipelineRun. Check the following in order:

| Check | Expected result | Action if it differs |
| --- | --- | --- |
| PipelineRun queue label | `kueue.x-k8s.io/queue-name` names a LocalQueue in the same namespace. | Create the missing LocalQueue or correct future submissions. Review CEL routing if it replaced the label. |
| LocalQueue binding | `spec.clusterQueue` names the intended ClusterQueue. | Create a new LocalQueue if the immutable binding is wrong, and select it for new runs. |
| Namespace eligibility | The ClusterQueue selector matches the namespace labels. | Correct the selector or namespace labels through the administrator-managed configuration. |
| Queue conditions | The LocalQueue and ClusterQueue are active and permit admission. | Check referenced flavors, queue stop policies, and condition messages. |
| Quota | Every requested resource has a matching flavor and sufficient capacity. | Wait for active work to finish or adjust quota. See [Resource Requests](#resource_requests). |
| Kueue integration | `integrations.externalFrameworks` contains `PipelineRun.v1.tekton.dev`. | Update Kueue through its plugin configuration and wait for its controller to become ready. |
| Scheduler lifecycle | Scheduler remains enabled while queued work exists. | Restore the component if it was removed before managed runs finished. |

`QuotaReserved=False` indicates that quota has not been reserved; its reason and message explain why. Inspect `status.admission` and `Admitted` if quota is reserved but execution has not started. A waiting PipelineRun should have `spec.status: PipelineRunPending` and no TaskRun or execution Pod.

## Check resource requests \{#resource_requests}

Compare all `kueue.konflux-ci.dev/requests-*` PipelineRun annotations with the Workload requests under `spec.podSets[].template.spec.containers[].resources.requests` and the selected ClusterQueue's `spec.resourceGroups`.

- The concurrency resource `tekton.dev/pipelineruns` normally requests one unit per run. A count-only queue cannot admit a run that also requests CPU, memory, or custom capacity absent from that queue.
- A request must fit every requested dimension. Free concurrency slots do not help when the CPU or memory budget is exhausted.
- Resource quantities must use valid Kubernetes syntax, such as `500m`, `2`, or `4Gi`. Malformed annotations can prevent the controller from constructing the Workload.
- Pod requests and limits do not populate these PipelineRun annotations automatically. A missing annotation means the corresponding resource is not accounted for by Scheduler.

Correct the configuration for future submissions. If an existing run contains incorrect requests or queue selection, cancel it through Tekton and submit a corrected run after its Workload cleanup; do not edit an admitted Workload manually. See [Resource Quotas](../guides/resource_quotas.mdx).

## Check priority classes \{#priority_classes}

If the PipelineRun has `kueue.x-k8s.io/priority-class`, verify that the referenced class exists before inspecting admission order:

```bash
kubectl get pipelinerun <run> -n <namespace> --show-labels
kubectl get workloadpriorityclass <class> -o yaml
kubectl get workloads -n <namespace> -o yaml
```

Compare the Workload priority values, queue selections, and condition messages. A higher-priority waiting run competes with other runs in the same ClusterQueue; it does not obtain capacity from an independent queue or automatically interrupt already admitted work. If a class is missing and no Workload is created, inspect the Scheduler controller logs and create the required class.

## Configuration errors \{#configuration_errors}

Check the configuration at each stage of synchronization and read the webhook logs:

```bash
kubectl get tektonconfig config -o jsonpath='{.spec.scheduler}'
kubectl get tektonscheduler scheduler -o yaml
# SCHEDULER_NAMESPACE is the operator's configured component namespace.
SCHEDULER_NAMESPACE=$(kubectl get tektonconfig config -o jsonpath='{.spec.targetNamespace}')
kubectl get configmap tekton-kueue-config -n "$SCHEDULER_NAMESPACE" \
  -o go-template='{{index .data "config.yaml"}}'
kubectl logs -n "$SCHEDULER_NAMESPACE" deployment/tekton-kueue-webhook --tail=100
kubectl logs -n "$SCHEDULER_NAMESPACE" deployment/tekton-kueue-controller-manager --tail=100
```

| Symptom | Likely cause | Recovery |
| --- | --- | --- |
| Configuration reload fails. | Empty queue name, malformed configuration, or CEL compile error. | Correct TektonConfig and wait for a successful reload. The last successfully loaded policy remains active after a failed reload. |
| A run is rejected with a CEL evaluation error. | Access to an absent field, invalid value, wrong function argument type, or unexpected expression result. | Guard optional fields and return a mutation, a list of mutations, or `[]`. Preview a corrected run with server-side dry run. |
| The run uses an unexpected queue or priority. | An existing CEL rule replaced a supplied or default label, or a new policy has not loaded yet. | Check the complete expression array and webhook reload logs, then inspect a newly created run. |
| A custom resource request is incorrect. | Duplicate `resource()` rules added their integer values. | Review all matching expressions and any preexisting request annotation. |

Fix configuration through TektonConfig rather than editing its generated ConfigMap. A Ready child resource does not confirm successful loading of a newly edited policy. See [Configure CEL](../guides/configure_cel.mdx#evaluation_behavior) for evaluation and mutation order.

## Submission fails \{#submission_fails}

An unavailable admission webhook can reject PipelineRun creation in enrolled namespaces. Inspect Scheduler deployments, services, certificates, and the webhook configuration:

```bash
kubectl get deployments,services,certificates -n <target-namespace>
kubectl get mutatingwebhookconfiguration tekton-kueue-mutating-webhook-configuration -o yaml
kubectl logs -n <target-namespace> deployment/tekton-kueue-webhook --tail=100
```

Read the component namespace from `TektonConfig.spec.targetNamespace`. Check image pull errors, certificate readiness, the webhook CA bundle, and Service endpoints. For CEL-specific errors, follow [Configuration Errors](#configuration_errors). Restore the failed dependency before retrying the submission.

Removing namespace enrollment lets new submissions bypass scheduling and removes that namespace's concurrency protection. It does not resume runs that are already pending.

## Run bypasses scheduling \{#run_bypasses_scheduling}

Verify that Scheduler is enabled and the namespace had `tekton.dev/scheduler-enabled: "true"` when the run was created:

```bash
kubectl get tektonconfig config -o jsonpath='{.spec.scheduler.disabled}'
kubectl get namespace <namespace> --show-labels
kubectl get pipelinerun <run> -n <namespace> -o yaml
```

Runs created before enrollment continue with their original execution behavior. A queue label alone does not enroll a namespace in the webhook. Apply the namespace label only after its queues are ready.

## Observe policy health \{#policy_health}

If webhook metrics are collected by the cluster monitoring system, use these counters to distinguish policy loading, evaluation, and mutation errors. Each has a `result` label with `success` or `failure` values:

| Counter | Meaning |
| --- | --- |
| `tekton_kueue_config_reload_total` | Configuration reload attempts. |
| `tekton_kueue_cel_evaluations_total` | CEL evaluations. |
| `tekton_kueue_cel_mutations_total` | CEL mutation application. |

An increase in failures is a reason to inspect webhook logs and the recently changed policy. Queue and Workload conditions remain the primary source for quota and admission diagnostics.
