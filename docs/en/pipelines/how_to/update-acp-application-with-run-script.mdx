# Update ACP Application with Existing Image and Run Script Task

## Feature Overview

This guide shows how to update an existing ACP `Application` by reusing the built-in `run-script` Task and selecting an existing runtime image from the tool image selector.

This is useful when you want to:

- Keep using the existing `run-script` execution model.
- Avoid creating a custom Task for a one-step update operation.
- Reuse the built-in `kubectl-app-manager` image option that is already registered for `run-script`.

## Use Cases

- Update image tags, replicas, environment variables, or labels in an existing ACP `Application` manifest.
- Apply a small patch to an existing ACP `Application` in a delivery pipeline.
- Execute a controlled `Application` update as a single pipeline stage.

## Prerequisites

- Tekton Pipelines is installed and running.
- You can run `TaskRun` or `PipelineRun` in the target namespace.
- The target ACP `Application` already exists.
- Your ServiceAccount has permissions to `get`, `patch`, and `update` the target `Application`.
- For Approach B, if your manifest may create new resources, the ServiceAccount also needs `create` permission on those resources.

For image selection and tool image details, see [Built-in Tool Images Selection Guide](./tool-images.mdx).
For remote Task references, see [Specifying remote tasks using hub resolvers](./specifying_remote_tasks_using_hub_resolvers.mdx).

## Required Inputs and How to Get Them

Before running any YAML in this guide, collect the following values.

| Input | Why it is required | How to get it |
| --- | --- | --- |
| `<RUN_NAMESPACE>` | Namespace where `TaskRun`/`PipelineRun` will run | Choose your pipeline namespace, for example `devops-ci`. |
| `<SA_NAME>` | ServiceAccount used by Tekton run | Use existing SA (for example `default`), or ask platform admin for the SA used by your pipeline runtime. |
| `<APP_NAMESPACE>` | Namespace of target ACP Application | From UI resource detail page or `kubectl get ns`. |
| `<APP_NAME>` | Target ACP Application name | From UI or `kubectl -n <APP_NAMESPACE> get <APP_RESOURCE>`. |
| `<APP_RESOURCE>` | Exact kubectl resource name (for example `applications.app.k8s.io`) | See the command below this table. |
| `<PATCH_JSON>` | Merge patch content to apply | Build from your real schema. First export current object: `kubectl -n <APP_NAMESPACE> get <APP_RESOURCE> <APP_NAME> -o yaml > app-before.yaml`, then prepare merge patch JSON. |
| `<REPOSITORY>` / `<REVISION>` / `<APPLICATION_FILE>` | Needed only for Approach B (Pipeline-based Git flow) | From your Git repo URL/branch and manifest file path in repo. |

To find `<APP_RESOURCE>`, list namespaced API resources and filter by name:

```bash
kubectl api-resources --namespaced -o name | grep -i -E 'application|appdeploy|oam'
```

Example output (will differ per cluster):

```text
applications.app.k8s.io
appdeploys.app.example.io
```

Pick the one that matches your platform, then verify with:

```bash
kubectl -n <APP_NAMESPACE> get <APP_RESOURCE> <APP_NAME>
```

Example patch JSON:

```json
{"metadata":{"labels":{"release":"2026-04"}}}
```

If your schema supports image field update under `spec.components[*].properties.image`, your patch may look like:

```json
{"spec":{"components":[{"name":"web","properties":{"image":"registry.example.com/project/demo:1.2.3"}}]}}
```

To avoid YAML/quote escaping issues, prefer YAML block style when filling `patch-json` params (Approach B):

```yaml
- name: patch-json
  value: |-
    {"metadata":{"labels":{"release":"2026-04"}}}
```

## Permission Check (Recommended Before Running YAML)

The Task runs as `<SA_NAME>` in `<RUN_NAMESPACE>` and calls the Kubernetes API from inside a pod. It needs `get`, `patch`, and `update` on `<APP_RESOURCE>` in `<APP_NAMESPACE>` (plus `create` if your Approach B manifest may add new resources).

### Option 1: Inspect RoleBindings directly (most reliable)

List bindings in the target namespace that reference your ServiceAccount, then inspect the bound Role(s):

```bash
# Find bindings that grant permissions to the SA
kubectl -n <APP_NAMESPACE> get rolebinding -o json | \
  jq -r '.items[] | select((.subjects // [])[] | .kind=="ServiceAccount" and .name=="<SA_NAME>" and .namespace=="<RUN_NAMESPACE>") | .roleRef.kind + "/" + .roleRef.name'

# For each roleRef returned above, dump the rules and check for <APP_RESOURCE>
kubectl -n <APP_NAMESPACE> get role <ROLE_NAME> -o jsonpath='{.rules}' | jq
# (or `kubectl get clusterrole <NAME> ...` if the binding references a ClusterRole)
```

If no binding is returned, or the bound role lacks the required verbs on `<APP_RESOURCE>`, ask your cluster admin to grant RBAC before continuing. A minimal Role looks like:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: acp-app-updater
  namespace: <APP_NAMESPACE>
rules:
  - apiGroups: ["<API_GROUP>"]          # e.g. app.k8s.io
    resources: ["<RESOURCE_PLURAL>"]    # e.g. applications
    verbs: ["get", "patch", "update"]   # add "create" for Approach B if needed
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: acp-app-updater
  namespace: <APP_NAMESPACE>
subjects:
  - kind: ServiceAccount
    name: <SA_NAME>
    namespace: <RUN_NAMESPACE>
roleRef:
  kind: Role
  name: acp-app-updater
  apiGroup: rbac.authorization.k8s.io
```

### Option 2: Quick `kubectl auth can-i` pre-flight (vanilla Kubernetes only)

```bash
kubectl -n <APP_NAMESPACE> auth can-i get <APP_RESOURCE> --as=system:serviceaccount:<RUN_NAMESPACE>:<SA_NAME>
kubectl -n <APP_NAMESPACE> auth can-i patch <APP_RESOURCE> --as=system:serviceaccount:<RUN_NAMESPACE>:<SA_NAME>
kubectl -n <APP_NAMESPACE> auth can-i update <APP_RESOURCE> --as=system:serviceaccount:<RUN_NAMESPACE>:<SA_NAME>
```

Expected output when RBAC is sufficient — each command prints a single line:

```text
yes
yes
yes
```

> **Important — do not rely on this on ACP / managed distributions.** On ACP the user-facing API is fronted by an authentication gateway that does **not** honor `--as` impersonation: the check executes with the caller's own identity rather than the impersonated ServiceAccount, so all three commands return `yes` even when the SA has no RBAC at all. Verified on ACP by running `kubectl auth can-i delete nodes --as=system:serviceaccount:<ns>:default` (returns `yes`). Prefer Option 1 above, or run the TaskRun and inspect the pod logs for `Error from server (Forbidden)` messages (see Troubleshooting).

> The `--as=` flag additionally requires the caller itself to have `impersonate` permission on `serviceaccounts`. If you see an error like `Error from server (Forbidden): User "..." cannot impersonate resource "serviceaccounts"`, ask a cluster admin to run the check for you, or grant yourself the appropriate impersonation role.

If your Approach B manifest may create resources, also verify `create` permission (same caveats apply).

If `application-file` contains multiple resource kinds, repeat the checks for each kind in that file.

## Choosing an Approach

This guide provides two approaches. Pick the one that fits your workflow:

| | Approach A: TaskRun (Direct) | Approach B: Pipeline (Git-Managed) |
| --- | --- | --- |
| **Best for** | One-off or ad-hoc updates | Repeatable, auditable updates in a CI/CD flow |
| **Source of truth** | Inline patch JSON only | Application manifest stored in Git, with optional patch overlay |
| **Resources created** | 1 `TaskRun` | 1 `Pipeline` + 1 `PipelineRun` |
| **Git clone needed** | No | Yes |

## Approach A: Update Application with TaskRun (Direct)

Use this approach for a one-off update where you supply the patch directly in the YAML.

Save the following as `taskrun.yaml` and replace all `<PLACEHOLDER>` values with the inputs collected above:

```yaml
# taskrun.yaml
apiVersion: tekton.dev/v1
kind: TaskRun
metadata:
  name: update-acp-application-direct
  namespace: <RUN_NAMESPACE>
spec:
  serviceAccountName: <SA_NAME>
  params:
    - name: image
      value: registry.alauda.cn:60070/devops/tektoncd/hub/kubectl-app-manager:v0.1
    - name: imagePullPolicy
      value: Always
    - name: args
      value:
        - |-
          <PATCH_JSON>
    - name: script
      value: |
        set -euo pipefail

        APP_RESOURCE="<APP_RESOURCE>"
        APP_NAME="<APP_NAME>"
        APP_NS="<APP_NAMESPACE>"
        if [ $# -ge 1 ]; then PATCH_JSON="$1"; else PATCH_JSON="{}"; fi

        echo "Checking application existence: ${APP_NS}/${APP_RESOURCE}/${APP_NAME}"
        kubectl -n "${APP_NS}" get "${APP_RESOURCE}" "${APP_NAME}" >/dev/null

        if [ "${PATCH_JSON}" = "{}" ] || [ -z "${PATCH_JSON}" ]; then
          echo "PATCH_JSON is empty object; skip patch"
        else
          echo "Applying merge patch"
          kubectl -n "${APP_NS}" patch "${APP_RESOURCE}" "${APP_NAME}" --type merge -p "${PATCH_JSON}"
        fi

        echo "Verifying update result"
        kubectl -n "${APP_NS}" get "${APP_RESOURCE}" "${APP_NAME}" -o yaml | tee /tmp/application-after.yaml
        echo -n "updated: ${APP_NS}/${APP_RESOURCE}/${APP_NAME}" > "$(results.string-result.path)"
  taskRef:
    resolver: hub
    params:
      - name: kind
        value: task
      - name: catalog
        value: catalog
      - name: name
        value: run-script
      - name: version
        value: "0.1"
```

Apply it:

```bash
kubectl apply -f taskrun.yaml
```

Expected output:

```text
taskrun.tekton.dev/update-acp-application-direct created
```

> The `run-script` Task declares a `string-result` result. `$(results.string-result.path)` inside the user-supplied `script` param is resolved by Tekton together with all other variable references when the final pod spec is materialized, so it correctly points at the result file path at runtime. The same mechanism is used in `testing/features/testdata/pipeline/tr-resolver-run-script.yaml`.

## Approach B: Update Application in Pipeline (Git-Managed)

Use this approach when the Application manifest is version-controlled in Git and you want a repeatable pipeline.

### Step 1 - Create the Pipeline

Save the following as `pipeline.yaml` and replace `<RUN_NAMESPACE>`:

```yaml
# pipeline.yaml
apiVersion: tekton.dev/v1
kind: Pipeline
metadata:
  name: update-acp-application
  namespace: <RUN_NAMESPACE>
spec:
  params:
    - name: repository
      type: string
    - name: revision
      type: string
      default: main
    - name: app-resource
      type: string
    - name: app-name
      type: string
    - name: app-namespace
      type: string
    - name: patch-json
      type: string
      default: "{}"
    - name: application-file
      type: string
      default: manifests/application.yaml
    - name: script-image
      type: string
      default: registry.alauda.cn:60070/devops/tektoncd/hub/kubectl-app-manager:v0.1
  tasks:
    - name: fetch-source
      taskRef:
        resolver: hub
        params:
          - name: kind
            value: task
          - name: catalog
            value: catalog
          - name: name
            value: git-clone
          - name: version
            value: "0.9"
      params:
        - name: url
          value: $(params.repository)
        - name: revision
          value: $(params.revision)
        - name: sslVerify
          value: "false"
      workspaces:
        - name: output
          workspace: source
    - name: update-application
      runAfter:
        - fetch-source
      taskRef:
        resolver: hub
        params:
          - name: kind
            value: task
          - name: catalog
            value: catalog
          - name: name
            value: run-script
          - name: version
            value: "0.1"
      params:
        - name: image
          value: $(params.script-image)
        - name: imagePullPolicy
          value: Always
        - name: args
          value:
            - $(params.patch-json)
        - name: script
          value: |
            set -euo pipefail
            APP_FILE="/workspace/source/$(params.application-file)"
            if [ $# -ge 1 ]; then PATCH_JSON="$1"; else PATCH_JSON="{}"; fi
            kubectl -n "$(params.app-namespace)" get "$(params.app-resource)" "$(params.app-name)" >/dev/null
            if [ ! -f "${APP_FILE}" ]; then echo "ERROR: file not found: ${APP_FILE}"; exit 1; fi
            kubectl -n "$(params.app-namespace)" apply -f "${APP_FILE}"
            if [ "${PATCH_JSON}" = "{}" ] || [ -z "${PATCH_JSON}" ]; then
              echo "PATCH_JSON is empty object; skip patch"
            else
              kubectl -n "$(params.app-namespace)" patch "$(params.app-resource)" "$(params.app-name)" --type merge -p "${PATCH_JSON}"
            fi
            kubectl -n "$(params.app-namespace)" get "$(params.app-resource)" "$(params.app-name)" >/dev/null
            echo -n "updated: $(params.app-namespace)/$(params.app-resource)/$(params.app-name)" > "$(results.string-result.path)"
      workspaces:
        - name: source
          workspace: source
  workspaces:
    - name: source
```

Apply it:

```bash
kubectl apply -f pipeline.yaml
```

Expected output:

```text
pipeline.tekton.dev/update-acp-application created
```

> In the `script` param above, both `$(params.*)` and `$(results.string-result.path)` are resolved by Tekton during variable substitution when the final pod spec is materialized. The `run-script` Task's own step script uses the same `$(results.string-result.path)` form (see `catalog/task/run-script/0.1/run-script.yaml`), so this pattern is guaranteed to work.

### Step 2 - Create the PipelineRun

#### Public Git Repository

Save the following as `pipelinerun.yaml` and replace all `<PLACEHOLDER>` values:

```yaml
# pipelinerun.yaml
apiVersion: tekton.dev/v1
kind: PipelineRun
metadata:
  name: update-acp-application-run
  namespace: <RUN_NAMESPACE>
spec:
  taskRunTemplate:
    serviceAccountName: <SA_NAME>
  pipelineRef:
    name: update-acp-application
  params:
    - name: repository
      value: <REPOSITORY>
    - name: revision
      value: <REVISION>
    - name: app-resource
      value: <APP_RESOURCE>
    - name: app-name
      value: <APP_NAME>
    - name: app-namespace
      value: <APP_NAMESPACE>
    - name: application-file
      value: <APPLICATION_FILE>
    - name: patch-json
      value: |-
        <PATCH_JSON>
  workspaces:
    - name: source
      volumeClaimTemplate:
        spec:
          accessModes:
            - ReadWriteOnce
          resources:
            requests:
              storage: 1Gi
```

Apply it:

```bash
kubectl apply -f pipelinerun.yaml
```

Expected output:

```text
pipelinerun.tekton.dev/update-acp-application-run created
```

#### Private Git Repository

If your repository is private, you need to provide git credentials and add a `git-auth` workspace.

1. Create the git credentials secret:

   ```bash
   kubectl -n <RUN_NAMESPACE> create secret generic git-basic-auth \
     --type kubernetes.io/basic-auth \
     --from-literal=username='<GIT_USERNAME>' \
     --from-literal=password='<GIT_PASSWORD_OR_TOKEN>'
   ```

   Expected output:

   ```text
   secret/git-basic-auth created
   ```

2. Modify the Pipeline from Step 1 by making two changes, then re-apply it:

   **Change a)** — In the `fetch-source` task, add the `basic-auth` workspace binding:

   ```yaml
         workspaces:
           - name: output
             workspace: source
           # Add this line:
           - name: basic-auth
             workspace: git-auth
   ```

   **Change b)** — At the bottom of `spec.workspaces`, add the `git-auth` workspace:

   ```yaml
     workspaces:
       - name: source
       # Add this line:
       - name: git-auth
   ```

   Then re-apply:

   ```bash
   kubectl apply -f pipeline.yaml
   ```

   Expected output (note the `configured` verb because the Pipeline already exists):

   ```text
   pipeline.tekton.dev/update-acp-application configured
   ```

3. Use the PipelineRun below instead of the public-repo version. Save it as `pipelinerun-private.yaml` and replace all `<PLACEHOLDER>` values:

   ```yaml
   # pipelinerun-private.yaml
   apiVersion: tekton.dev/v1
   kind: PipelineRun
   metadata:
     name: update-acp-application-run
     namespace: <RUN_NAMESPACE>
   spec:
     taskRunTemplate:
       serviceAccountName: <SA_NAME>
     pipelineRef:
       name: update-acp-application
     params:
       - name: repository
         value: <REPOSITORY>
       - name: revision
         value: <REVISION>
       - name: app-resource
         value: <APP_RESOURCE>
       - name: app-name
         value: <APP_NAME>
       - name: app-namespace
         value: <APP_NAMESPACE>
       - name: application-file
         value: <APPLICATION_FILE>
       - name: patch-json
         value: |-
           <PATCH_JSON>
     workspaces:
       - name: source
         volumeClaimTemplate:
           spec:
             accessModes:
               - ReadWriteOnce
             resources:
               requests:
                 storage: 1Gi
       - name: git-auth
         secret:
           secretName: git-basic-auth
   ```

   Apply it:

   ```bash
   kubectl apply -f pipelinerun-private.yaml
   ```

   Expected output:

   ```text
   pipelinerun.tekton.dev/update-acp-application-run created
   ```

## Validation

After execution, verify the run status and the updated Application.

For **Approach A** (TaskRun):

```bash
kubectl -n <RUN_NAMESPACE> get taskrun update-acp-application-direct
```

Expected output — `SUCCEEDED` should be `True` and `REASON` should be `Succeeded`:

```text
NAME                            SUCCEEDED   REASON      STARTTIME   COMPLETIONTIME
update-acp-application-direct   True        Succeeded   2m          30s
```

For **Approach B** (PipelineRun):

```bash
kubectl -n <RUN_NAMESPACE> get pipelinerun update-acp-application-run
```

Expected output:

```text
NAME                         SUCCEEDED   REASON      STARTTIME   COMPLETIONTIME
update-acp-application-run   True        Succeeded   3m          1m
```

Then confirm the Application has been updated:

```bash
kubectl -n <APP_NAMESPACE> get <APP_RESOURCE> <APP_NAME> -o yaml
```

To inspect the `string-result` result written by `run-script`:

```bash
# For Approach A
kubectl -n <RUN_NAMESPACE> get taskrun update-acp-application-direct -o jsonpath='{.status.results}'
```

Expected output — the `run-script` Task declares four results (`array-result`, `object-result`, `string-result`, `overview-markdown`) and initializes the first three, so you will see all of them. Your script populates `string-result`:

```text
[{"name":"array-result","type":"array","value":[]},{"name":"object-result","type":"object","value":{}},{"name":"string-result","type":"string","value":"updated: <APP_NAMESPACE>/<APP_RESOURCE>/<APP_NAME>"}]
```

To extract just `string-result` for easier reading:

```bash
kubectl -n <RUN_NAMESPACE> get taskrun update-acp-application-direct \
  -o jsonpath='{.status.results[?(@.name=="string-result")].value}'
```

Expected output:

```text
updated: <APP_NAMESPACE>/<APP_RESOURCE>/<APP_NAME>
```

For Approach B, the `run-script` Task is wrapped by a TaskRun owned by the PipelineRun. Query it via labels:

```bash
# For Approach B (query the TaskRun created for pipeline task `update-application`)
TR_NAME=$(kubectl -n <RUN_NAMESPACE> get taskrun \
  -l tekton.dev/pipelineRun=update-acp-application-run,tekton.dev/pipelineTask=update-application \
  -o jsonpath='{.items[0].metadata.name}')
kubectl -n <RUN_NAMESPACE> get taskrun "${TR_NAME}" \
  -o jsonpath='{.status.results[?(@.name=="string-result")].value}'
```

Expected output:

```text
updated: <APP_NAMESPACE>/<APP_RESOURCE>/<APP_NAME>
```

## Rollback

If the new configuration is not expected, patch the previous image back:

```bash
kubectl -n <APP_NAMESPACE> patch <APP_RESOURCE> <APP_NAME> --type merge -p '<PREVIOUS_PATCH_JSON>'
```

For safer rollback in production, keep the previous manifest version in Git and apply it directly.

## Troubleshooting

### Permission denied when using custom image

The `run-script` Task runs as non-root user `65532`. If your chosen image is not compatible with non-root, the Task may fail.

Use the built-in `kubectl-app-manager` image first, or adjust your custom image. See:
- [Permission Issues When Using Custom Images in run-script Task](../trouble_shooting/custom_images_cannot_be_used_in_the_run-script.mdx)
- [Adjust Containerfile for Building Task-Compatible Custom Images](./adjust_containerfile_for_task_compatible_image.mdx)

### TaskRun / PipelineRun fails with `Error from server (Forbidden)`

Pods launched by Tekton call the in-cluster Kubernetes API server using the ServiceAccount's projected token, which is **not** subject to the ACP API gateway's auth layer. RBAC that "seems fine" via `kubectl auth can-i --as=` from your workstation may not actually exist on the in-cluster API server.

1. Fetch the step logs to confirm the exact verb, resource, and SA that was denied:

   ```bash
   # Approach A
   kubectl -n <RUN_NAMESPACE> logs update-acp-application-direct-pod -c step-run-script

   # Approach B (find the wrapped TaskRun first)
   TR_NAME=$(kubectl -n <RUN_NAMESPACE> get taskrun \
     -l tekton.dev/pipelineRun=update-acp-application-run,tekton.dev/pipelineTask=update-application \
     -o jsonpath='{.items[0].metadata.name}')
   kubectl -n <RUN_NAMESPACE> logs "${TR_NAME}-pod" -c step-run-script
   ```

   Typical message:

   ```text
   Error from server (Forbidden): applications.app.k8s.io "review-demo" is forbidden: User "system:serviceaccount:<RUN_NAMESPACE>:<SA_NAME>" cannot get resource "applications" in API group "app.k8s.io" in the namespace "<APP_NAMESPACE>"
   ```

2. Inspect the RoleBindings and Roles in `<APP_NAMESPACE>` for `<SA_NAME>` (see *Permission Check — Option 1*). If no binding exists, ask a cluster admin to apply the sample `Role` + `RoleBinding` shown there.

### Application not found

Confirm target namespace and resource name:

```bash
kubectl -n <APP_NAMESPACE> get <APP_RESOURCE> <APP_NAME>
```

### Patch path does not match your Application schema

Use this sequence to build a correct patch:

```bash
kubectl -n <APP_NAMESPACE> get <APP_RESOURCE> <APP_NAME> -o yaml > app-before.yaml
```

Then create `PATCH_JSON` from your real object structure and apply again.

### PipelineRun rejected with `strict decoding error: unknown field "spec.serviceAccountName"`

On Tekton v1 the ServiceAccount field moved from `spec.serviceAccountName` to `spec.taskRunTemplate.serviceAccountName`. Clusters that enable strict schema decoding will reject the old form. Use:

```yaml
spec:
  taskRunTemplate:
    serviceAccountName: <SA_NAME>
```

### Pipeline not found when creating PipelineRun

If you see an error like `pipeline "update-acp-application" not found`, make sure you applied the Pipeline resource (Step 1) before creating the PipelineRun (Step 2):

```bash
kubectl -n <RUN_NAMESPACE> get pipeline update-acp-application
```

Expected output when the Pipeline exists:

```text
NAME                     AGE
update-acp-application   30s
```

If the command returns `Error from server (NotFound): pipelines.tekton.dev "update-acp-application" not found`, re-apply `pipeline.yaml` from Step 1.
